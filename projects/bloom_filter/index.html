Bloom filters, and where the bits actually go

I wrote three of them in C, measured every claim I could find, and drew the pictures that finally made the thing click for me. Everything below runs in your browser, and every number comes from a benchmark you can rerun.

The problem

Most of the time, the answer is no

At work I maintain a retrieval system over a knowledge graph with about fifteen thousand entities in it. A big part of what it does all day is ask a very boring question: have I already processed this thing? And the honest answer, almost always, is no.

That asymmetry is everywhere once you start noticing it. A web crawler asking whether it has seen a URL. A storage engine asking whether a key might live in some file on disk. A password service asking whether a string appears in a breach list. Each one is a membership test where the overwhelming majority of answers are no, and where the cost of finding that out is dominated by a data structure you had to keep in memory.

The obvious fix is a hash set. It works, and it is exact, and for a long time that is what I reached for without thinking. Then I actually measured what it costs. Storing ten million 16-byte keys means writing down 160 MB of keys before you have added a single byte of structure, and my open-addressed implementation actually allocates once the capacity rounds up to a power of two. Every lookup that misses still has to touch a random cache line somewhere in that, which on my laptop costs once the table stops fitting in cache.

A Bloom filter answers the same question for the same ten million keys in . That is less memory than my hash set, and still less than the theoretical floor for anything exact. The catch is that it sometimes says yes when it means no. How often is a number you get to choose, and the whole design is about buying that number as cheaply as possible.

The deal

A Bloom filter never misses something you inserted. It occasionally claims to have something you did not insert. You trade a controllable error rate in one direction for an enormous amount of memory.

What follows is the version of this I wish I had read first. The pictures are interactive, the math is derived rather than asserted, and the performance section is measured on real hardware rather than reasoned about. Where my measurements disagreed with what I expected, I kept the measurement.

The trick

An array of bits and a few hash functions

Here is the entire idea. Take an array of m bits, all zero. Pick k hash functions. To insert a key, hash it k times, and set those k bits to 1. To ask whether a key is present, hash it the same k ways and look. If any of those bits is 0, the key was definitely never inserted. If all of them are 1, it probably was.

That is the whole data structure. There is no bucket, no chain, no key storage, no resizing. The keys themselves are never written down anywhere, which is why the memory does not grow with how long your keys are.

The guarantee

Why it can be wrong in only one direction

This part took me embarrassingly long to internalise, and it comes down to one property: bits only ever go from 0 to 1. Nothing in the insert path ever clears a bit.

So if I inserted a key, I set its k bits, and from that moment on those bits are 1 forever. When I later query that key, I look at exactly those same k positions, and they cannot have changed back. The filter must say yes. A false negative is not unlikely, it is impossible.

The reverse has no such protection. A key I never inserted hashes to k positions that other keys may have set for their own reasons. If all k of them happen to be occupied, the filter says yes and it is wrong.

A yes means "maybe". A no means "definitely not". Every correct use of a Bloom filter is built on trusting the no and verifying the yes.

That last sentence is the practical shape of every real deployment. You put the filter in front of something expensive. When it says no, you skip the expensive thing, and you are always right to. When it says yes, you do the expensive thing, and occasionally you did it for nothing.

The math

Three knobs, one number

There are only three things to choose: how many keys you expect (n), how many bits you are willing to spend (m), and how many hash functions you use (k). Everything else follows.

Step one: how full does the array get?

Inserting one key sets k bits. Pick any single bit in the array. The chance that one particular hash misses it is 1 - 1/m. Across k hashes for n keys, that is kn independent chances to miss, so the probability that our bit is still 0 is

P(bit is still 0) = (1 - 1/m)^(kn)  ≈  e^(-kn/m)

The approximation is the usual one, and it is extremely good for any m you would actually use. So the fraction of the array that ends up set is 1 - e^(-kn/m). My implementation counts the set bits after loading two million keys, and it lands on that curve to three decimal places every time.

Step two: how often do all k bits collide?

For a key that was never inserted, a false positive means all k of its positions happen to be set. Treating those as independent gives the formula you will find everywhere:

false positive rate  ≈  (1 - e^(-kn/m))^k

Step three: the best k

Two forces pull against each other. More hash functions means more bits a false positive has to get lucky on, which helps. More hash functions also means every insert sets more bits, so the array fills faster, which hurts. Somewhere in the middle is a minimum.

Differentiate and the answer is clean:

k* = (m/n) · ln 2  ≈  0.693 · bits per key

At that point the array is exactly half full, which is a nice thing to remember. Half the bits are 1, half are 0, and the false positive rate is 0.5^k, or equivalently 0.6185^(m/n).

The tug of war why k has an optimum

Blue: more hashes make a lucky collision harder. Amber: more hashes fill the array faster. Pink is their product, the actual false positive rate.

The minimum sits where the two effects balance, at k = 0.693 × bits per key.

I measured this rather than trusting it. At 10 bits per key I built a filter for every k from 1 to 14 and threw twenty million never-inserted keys at each one. The minimum landed exactly where the formula says it should.

A correction

The formula everyone quotes is a lower bound

While I was checking my implementation against theory I kept finding my measured rates a hair above the formula, at every size, in a way that did not look like noise. It turns out this is a known result, and the formula in every tutorial is subtly wrong.

Here is the problem. The derivation computes the expected number of set bits, then plugs that expectation into (fill)^k. But the number of set bits is a random variable, and raising it to a power is a convex operation. By Jensen's inequality, the expectation of the power is at least the power of the expectation. So the real rate is always at least what the formula says.

Bose and colleagues proved this properly in 2008. The gap shrinks like 1/m, so on any filter big enough to be useful it is invisible. On small filters it is not. To see it I computed the exact rate with a little dynamic program over the distribution of set bits, then built three hundred thousand independent tiny filters at each size and measured what actually happened.

At m = 128 bits the textbook value is below the true rate. By m = 4096 the gap is under half a percent, and by the time you get to a real filter it is far below anything you could measure.

Why I am telling you this

Not because it will change your capacity planning. It will not. I am telling you because I spent an afternoon convinced I had a bug, and the bug was in the formula I was checking against. If your measured rate is a fraction of a percent above theory, that is not your hash function.

An implementation detail that matters

You do not need k hash functions

The description says "pick k independent hash functions", and if you take that literally you will hash every key seven times, which is seven times the work for no reason.

Kirsch and Mitzenmacher showed in 2006 that two are enough. Compute h1 and h2 once, then generate the rest arithmetically:

// two hashes, k positions, no extra hashing in the loop
uint64_t h1 = hash(key, len, seed);
uint64_t h2 = mix(h1) | 1;           // forced odd so it cycles fully
for (int i = 0; i < k; i++) {
    uint64_t bit = fastrange(h1, m); // multiply, not modulo
    bits[bit >> 6] |= 1ull << (bit & 63);
    h1 += h2;
}

The claim is that this costs you nothing in accuracy. I did not want to take that on faith, so I built both versions and measured them side by side at five different densities, each with enough probes to resolve the rate to a fraction of a percent.

bits/keykdouble hashingk real hashesdifferencespeed

The false positive rates are indistinguishable. The speed is not: the double-hashing version is meaningfully faster because it does one hash instead of k. This is the rare optimisation that is free.

The other detail in that snippet

fastrange is Lemire's trick for mapping a 64-bit value into a range: take the high half of a 128-bit multiply instead of doing a modulo. A % here is a division, which is roughly twenty cycles, and you are doing k of them per lookup. Replacing it with a multiply was worth more to my benchmark than anything else I changed.

Measurements

What it actually costs

Everything up to here is arithmetic. This part is a machine. All of the numbers below come from C compiled with -O3 -march=native on an Apple M5 Pro: seven repetitions with a warmup pass discarded, a volatile sink so nothing gets optimised away, and the fastest repetition reported rather than the median. That last choice is deliberate. Anything else running on the machine can only make a run slower, so the median still drifts upward when something wakes up. It bit me once: a point in my cache sweep came back at 39 ns against an otherwise smooth 17 ns trend. The minimum is the run where the least interference happened, which is the number I am after.

I implemented four things: a classic Bloom filter, a cache-blocked one, a register-blocked one, and an exact open-addressed hash set to compare against. The hash set stores the full 16-byte key, because a set that only stores a fingerprint is not exact either, it just has a very small error rate of its own. If you want a real zero, you pay for the bytes.

Read that table from the bottom up. My hash set spends per key, most of which is empty slots, because open addressing wants headroom and a power-of-two capacity rounds it up further. A perfect exact structure with no overhead at all would still spend 128 bits per key, because the keys are 16 bytes and it has to write them down. That is the floor, and it is fixed by your data rather than by your cleverness.

The filter is not bound by that floor, because it never writes the keys down. It spends whatever you decide, and the price of each halving of the error rate is a flat 1.44 bits per key. That is the real headline: the error rate falls exponentially in the memory you spend, and the exchange rate never changes.

The exchange rate

Every additional 1.44 bits per key cuts the false positive rate in half. Forever. Ten bits gets you about one in a hundred, twenty gets you about one in fifteen thousand, and thirty gets you about one in two million.

Where the time goes

The k probes are the problem

Here is the thing nobody mentions in the tutorials. A classic Bloom filter lookup does k reads at k unrelated addresses. Once the filter is bigger than cache, that is k separate trips to main memory for one membership test.

The fix is to give up a little accuracy for locality. Pick one block that fits in a single cache line, then put all k bits inside it. One memory access instead of k. The false positive rate gets worse, because keys that land in an unlucky block have less room to spread out, but the lookup touches one line.

The classic filter costs about two nanoseconds per extra probe. A trip to DRAM on this machine is closer to eighty. The gap is memory-level parallelism: the addresses of all k probes are computable from one hash, they do not depend on each other, and a modern out-of-order core will happily have all of them in flight at once. You are not paying k latencies, you are paying one latency plus a bit of bandwidth.

So the blocked filter still wins, but by at k=7 rather than the sevenfold speedup the cartoon implies. That is a real win and I would take it. It is just not the win I was told to expect, and the reason is that the "k cache misses" story quietly assumes a processor that stalls on every load.

The textbook cost model for Bloom filters was written for machines that could only have one memory request outstanding. Yours can have dozens.

How big should a block be?

If blocking trades accuracy for locality, the block size is the dial. I swept it from 64 bits up to 4096 on a sixteen-million-key filter. This machine has 128-byte cache lines, which is not the 64 that most of the literature assumes, so I was curious where the knee would be.

The false positive rate, meanwhile, moves by nearly a factor of three, from at a 64-bit block down to at 4096.

So on this machine the block size is close to a free choice, and the right move is to take the biggest block you can and pocket the accuracy. A 1024-bit block is exactly one cache line here and gets you to , within striking distance of the a classic filter achieves, while still reading one line. I would expect the flat part of that curve to be narrower on hardware with less memory-level parallelism, which is the same caveat as the previous section.

The limitation

You cannot remove anything

Clearing the bits for a key you want to delete would also clear bits that other keys are relying on, and those keys would start coming back as false negatives. That breaks the one guarantee the structure has.

The standard workaround is to store small counters instead of bits. Insert increments, delete decrements, and a position counts as set if its counter is nonzero. Four bits per counter is the usual choice, which makes the whole thing four times bigger and is often the end of the conversation.

Notice the counters that go to 2 or 3. Those are the shared positions, and they are exactly the reason a plain Bloom filter cannot support delete.

If deletion matters to you, a counting filter is usually the wrong answer in 2026. Cuckoo filters and quotient filters both support deletion, both store small fingerprints rather than raw bits, and at the error rates people actually use they are smaller than a Bloom filter, not four times bigger. The crossover is around 3% false positives: below that, a cuckoo filter wins on space as well as features. The catch is that they can fail to insert when they get full, and they are considerably more code.

The other workaround, which is what most production systems do, is to not delete. Rebuild the filter periodically from the source of truth, or keep a generation of filters and drop the oldest. If you are tempted to reach for deletion, check first whether you can reach for a rebuild instead.

Judgement

When I would not use one

The failure mode of a good idea is applying it everywhere. Here is where I would stop.

  • When the answer is usually yes. The whole value is skipping expensive work on a no. If ninety percent of your queries are hits, you are paying for a filter that almost never saves you anything, and you still do the expensive lookup afterwards.
  • When you cannot verify a yes. If there is no source of truth behind the filter, a false positive is not a wasted lookup, it is a wrong answer that reaches the user. This is the one that actually bites people.
  • When the set is small. At ten thousand keys my exact hash set answers a miss in while the classic filter takes . Everything fits in cache, so the set does one probe and wins, and the filter does seven and loses. A filter is a memory optimisation, and at that size there is nothing to optimise. The register-blocked variant is still the fastest thing on the chart, but it is fast for reasons that have nothing to do with saving memory.
  • When you need to delete. Discussed above. Use a cuckoo filter, or rebuild.
  • When you do not know n in advance. The false positive rate is a function of how full the filter is, and a filter sized for a million keys that receives ten million degrades to useless silently. Scalable Bloom filters exist for this, chaining filters of geometrically growing size, but the fixed-size version is what most libraries give you and it will not warn you.
  • When an adversary picks the keys. With a fixed, published hash function, anyone can generate keys that collide with a known-set element and force your false positive rate to one. If the input is untrusted, the hash needs a secret seed.

Where they genuinely shine is the case they were built for. LSM-tree storage engines put one in front of every SSTable so a read that misses does not touch the disk. Content delivery caches use them to avoid caching one-hit-wonders. Chrome carried one in the browser for Safe Browsing for years. All of those have the same shape: the no is the common case, the no is free, and something authoritative sits behind the yes.

Method

The bug that nearly published wrong numbers

Every chart above rests on the harness being correct, so it is worth saying how close I came to publishing numbers that were not.

The harness runs its correctness checks before it runs a single benchmark, on purpose. An early version of my hash function ended a 16-byte hash with a 128-bit multiply-fold whose second operand was zero, which made every key in the universe hash to the same value. The filters still worked. They had no false negatives, they returned plausible-looking answers, and the only symptom was that the hash set went quadratic and the benchmark appeared to hang. A Bloom filter with a broken hash does not crash, it just quietly produces numbers you might publish.

So the test binary checks the hash before it checks anything else: no collisions across a million distinct keys, chi-square on both the high and low bytes, and an avalanche test that flips each of the 128 input bits and counts how many of the 64 output bits move. It should be 32. Mine measures 31.996.

Caveats, honestly

Single machine, single thread, one microarchitecture. Apple Silicon has unusually deep memory-level parallelism and 128-byte cache lines, so the classic-versus-blocked gap is probably wider on a typical x86 server. Keys are synthetic 16-byte values, not real URLs. Everything is measured with the filter fully built and static, so nothing here says anything about concurrent inserts. If you rerun it somewhere else and get a different shape, I would like to know.

Closing

The part I keep coming back to

What I find genuinely beautiful about this structure is that it is barely a structure at all. There are no pointers, no buckets, no rebalancing, nothing to invalidate. It is an array of bits and a decision to accept a specific, quantified amount of being wrong.

Burton Bloom published it in 1970, in a five-page paper whose worked example was a hyphenation dictionary too large to keep in core memory. The tradeoff he described has not aged at all, because the ratio it exploits, between the cost of storing something and the cost of being occasionally wrong about it, is not a property of any particular hardware. The constants moved by six orders of magnitude and the shape of the answer did not move at all.

If you take one thing from this: the useful move is not "use a Bloom filter". It is noticing that your problem has an asymmetric answer distribution and an authoritative check sitting behind it. Once you see that shape, the filter is the easy part.
